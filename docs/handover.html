Authorisation

Who can do what

Roles say who someone is; permissions say what they may do. Every check in the system — the API's route guards and the UI's gating — asks about a permission, never a role, so moving a capability between roles is a change to this one table and nothing else.

It lives in packages/shared/src/rbac.ts, imported by both the browser and the server. The server re-derives permissions from the database on every request; the client uses the same table only to decide what to draw.

Operations

Running it

Everything, in containers

# set SESSION_SECRET in .env first
cp .env.example .env
docker compose up -d --build
docker compose exec api pnpm --filter @service-hub/api db:seed

The app is on localhost:8080. nginx serves the built app and proxies /api to the API container, so the session cookie is first-party and CORS never comes into it.

Locally, against containerised Postgres

pnpm install
docker compose up -d db
pnpm --filter @service-hub/shared build
pnpm --filter @service-hub/api db:migrate
pnpm --filter @service-hub/api db:seed
pnpm dev            # api :3001, web :5173

Vite proxies /api the same way nginx does, so the cookie behaves identically.

Checking it still works

pnpm typecheck && pnpm lint && pnpm build
pnpm --filter @service-hub/api test   # needs Postgres up

The API tests run the real server against a real database. The parts worth testing here live in Fastify hooks, cookies and Prisma queries — replacing those would test nothing.

Structure

How it fits together

apps/web         React 19 · Vite · TanStack Router · React Hook Form
apps/api         Fastify · Prisma · Postgres
packages/shared  Zod schemas · domain types · the RBAC table

The shared package is the reason for the split. A validation rule or a role's permissions are written once and used by both sides, so the browser and the server cannot disagree about what a rule means or what a role allows.

What a signed-in request does

browser → nginx → Fastify onRequest
  1. reject the write if Origin isn't ours
  2. HMAC the cookie token, look up the session
  3. re-derive permissions from the user's current roles
  4. route guard checks one permission → 403 or handler

Because step 3 happens per request rather than being baked into the session, a role change takes effect immediately — and changing someone's roles also revokes their sessions outright.

Security

Decisions worth knowing

Passwords use scrypt from Node's standard library

A proper memory-hard KDF, and no native module to compile in the image. Each hash stores its own parameters, so they can be raised later without invalidating existing passwords.

The database never stores a usable session token

The cookie carries a random token; only its HMAC is stored. A dumped database contains no live sessions, and rotating SESSION_SECRET revokes every session at once.

Sign-in failures give nothing away

A wrong password and an unknown address return the same message, and the unknown case still burns the hashing time — so neither the wording nor the response timing reveals who has an account.

The session cookie is httpOnly

Script cannot read it, so an XSS bug cannot walk off with a session. Set SameSite=lax, backed by an Origin check on every state-changing request.

The last administrator cannot be locked out

The final active Admin can't be demoted, deactivated, or deleted, and nobody can delete their own account.

Next

Switching to single sign-on

Everything around the identity check is already provider-agnostic: sessions, the user table, roles, and the guards do not care where a person came from.

Turning OIDC on means three things, all inside apps/api/src/auth/providers/:

  • Install openid-client and fill in beginLogin and completeLogin with an Authorization Code + PKCE flow.
  • Set AUTH_PROVIDER=oidc plus the four OIDC_* variables.
  • Nothing else. signIn in the web app already follows a redirect if the server returns one.

linkOrCreateUser maps an external identity onto our own user row — matching on issuer + subject first, then a verified email, otherwise creating an account with the weakest roles. That is what makes "their user directory or ours" a non-question: there is always a row here, and the provider supplies identity without ever supplying authorisation.

Never match on an unverified email, and never key a user on the email instead of the subject claim. Addresses get reassigned; doing either would hand one person another's account.
